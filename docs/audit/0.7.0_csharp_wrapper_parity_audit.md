# 0.7.0 C# Wrapper Parity Audit

Date: 2026-03-21

## Scope

Audit of `csharp/RustEtherNetIp` against current Rust FFI surface in `src/ffi.rs`.

## Summary

Wrapper coverage is strong for production paths.

- Core read/write APIs: implemented
- Route-path connect/set: implemented
- UDT APIs (`ReadUdt`, `WriteUdt`, `GetUdtDefinition`, member offset APIs): implemented
- Batch write/execute: implemented via native typed FFI JSON paths
- Batch config APIs: intentionally unsupported (`NotSupportedException`)

## Notes on Surface Mapping

Rust exposes both pointer-based and id-based introspection functions.
C# wrapper uses the `*_by_id` family for safety and ownership control:

- `eip_get_udt_definition_by_id`
- `eip_get_tag_attributes_by_id`
- `eip_discover_tags_detailed_by_id`

This is acceptable parity even though some non-`_by_id` exports are not directly declared in C#.

## Current Gaps / Partial Areas

1. `ReadTagsBatch(...)` in C# remains sequential type-probing fallback.
   - `WriteTagsBatch(...)` and `ExecuteBatch(...)` are native FFI-backed.
   - `ReadTagsBatch(...)` does not yet use a strongly-typed native contract.

2. Batch configuration APIs are currently unsupported in wrapper/runtime pair.
   - `ConfigureBatchOperations(...)` and `GetBatchConfig()` throw by design.

## Recommendation

For full wrapper parity milestone:

1. Introduce typed native read-batch contract in Rust FFI.
2. Switch C# `ReadTagsBatch(...)` to that native contract.
3. Either implement batch-config FFI APIs end-to-end or keep explicit unsupported contract and document as intentional.
