# 0.7.0 Hardening Gate

This document defines the release hardening gates for the unreleased `0.7.0` line.
Until all gates pass, the published stable version remains `0.6.3`.

## Scope

- Release line: `0.7.0` (unreleased)
- Stable published version during hardening: `0.6.3`
- Branch policy: hardening work lands on `main` with traceable commit history

## Operating Rules

1. No `0.7.0` version bump in published artifacts until all gates are green.
2. Every high-impact change must run the cross-language regression matrix.
3. Any gate failure blocks release candidate freeze.
4. All gate evidence must be attached as file artifacts or CI logs.

## Gate Checklist

Use this table as the release control list. All rows must be `PASS`.

## Step-by-Step Execution Plan

### Step 1 - Stabilize metadata and scripts

- Align `VERSION` and `Cargo.toml`.
- Remove stale hardcoded framework/output assumptions in build verification scripts.
- Confirm basic build verification runs end-to-end.

Output:
- Version consistency check passes.
- Build scripts produce correct native/C# artifact checks.

### Step 2 - Enforce regression matrix

- Define one canonical command sequence for Rust and C# validation.
- Run it for each high-impact change.
- Store logs per change/revision.

Output:
- Repeatable matrix execution with explicit pass/fail status.

### Step 3 - Expand failure-mode tests

- Add simulator-backed tests for:
  - Connection timeout behavior
  - Reconnect behavior after simulated failure
  - Partial batch failures with continue-on-error semantics

Output:
- Deterministic test outcomes with no flaky retries.

### Step 4 - Harden FFI contracts

- Add explicit FFI tests for:
  - Mixed read/write batch payloads
  - Malformed JSON payloads
  - Missing fields (`value_type`, `value`)
  - Invalid declared counts vs payload length

Output:
- Structured and deterministic error responses verified by tests.

### Step 5 - Confirm batch config API contract

- Keep current unsupported gating behavior unless full implementation is approved.
- Validate wrappers expose unsupported status clearly (no silent success behavior).
- Reflect status in docs.

Output:
- One consistent behavior across Rust FFI, C# wrapper, and docs.

### Step 6 - Build and publish performance baseline

- Execute benchmark scenarios for:
  - Single read/write
  - Batch read/write
  - Mixed execute batch
- Compare against `0.6.3` baseline in same environment.

Output:
- Baseline report with environment metadata and regression thresholds.

### Step 7 - Route-path and UDT compatibility pass

- Run route-path compatibility scenarios.
- Run UDT-heavy read/write workloads.
- Capture pass/fail matrix and error classifications.

Output:
- Compatibility evidence for production-like routing and UDT usage.

### Step 8 - Docs/API audit

- Audit README, examples, wrapper docs, and changelog claims.
- Correct mismatches immediately and re-verify.

Output:
- Documentation and runtime semantics are aligned.

### Step 9 - Freeze RC and promote

- Freeze candidate commit only after all gates pass.
- Re-run full gate set one final time.
- Then and only then bump/publish `0.7.0`.

Output:
- Signed release decision with complete evidence bundle.

## Safety Notes for Industrial Deployment

- Prefer deterministic simulator tests for failure handling before production-floor validation.
- Treat any reconnect behavior change as high-impact.
- Keep unsupported APIs explicit to prevent false operator assumptions.
- Require artifact-backed sign-off for every release gate.
