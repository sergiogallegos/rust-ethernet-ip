The read-only safety boundary was also exercised. Posting to

## Physical Cable-Disconnect Check

`confirmed` on 2026-08-23 after the dashboard reconnect-state hardening:

- removing the Ethernet cable produced one 10-second active-read timeout;
- the UI/API changed to `Reconnecting`, reported 0/39 good, disabled writes,
  and retained the last successful values with `Stale` quality;
- reconnect attempts used an 800 ms TCP endpoint probe while the cable was
  absent, avoiding a queue of full native connection timeouts;
- after the cable was restored, attempt 5 reached the endpoint, created a new
  routed native session, and completed a 39/39 good scan without restarting
  ASP.NET;
- the recovered browser-facing snapshot reported `Connected`, 39/39 good,
  zero stale signals, and a 146.37 ms scan;
- concurrent dashboard requests return the latest completed immutable snapshot
  rather than queuing behind an active PLC timeout.

The 10-second initial transition reflects the 1.2.1 native explicit-read
timeout. The example shortens repeated *reconnect* attempts without changing
that released native timeout contract.
